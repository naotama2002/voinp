# 08. 編集面と学習ループ

> ステータス: **設計方針**（未実装）。2026-09-20 に方針を決めた段階。

## これは何か

挿入する前に**確認して直せる面**を voinp に持たせ、その編集操作を
**用語辞書の学習信号として回収する**という設計。

音声入力ウィジェットの設計書（別プロジェクト向け、Web の業務システム）を
読んで、voinp に移せる部分と移せない部分を仕分けた結果として出てきた。

## なぜこれが要るのか

実測で分かっていること（[02](02-transcription.md) のクラウド比較）:

- 誤りの中心は **変換誤り（同音異義）と固有名詞**
- macOS もクラウドも**同じ語で同じように間違える**（`kintone` → 「均等の」）
- つまりエンジンを替えても直らない。**効くのは辞書**

そして辞書を育てるには、**何をどう直したか**が要る。
手で登録させ続けるのは続かない。

## 鍵になった気づき

当初、「voinp はテキストエリアを持っていないので学習ループは成立しない」と
判断していた。挿入は ⌘V かキーストロークで他アプリへ入れて終わりで、
その後ユーザーが何を直したかは観測できないため。

**これは切り分けが雑だった。** 挿入する前に voinp 自身の面で編集させれば、
編集前後が手元で取れる。

重要なのは、**他アプリを覗かないこと**。
[04](04-prompts.md) の「画面の内容を文脈に入れない」という脅威モデルに触れない。
AX で挿入先を監視する案は、この点で筋が悪い。

## ぶつかる場所

HUD は**意図的にキーフォーカスを取らない**作りになっている
（[05](05-ui-input.md) の勘所 6）。

```swift
override var canBecomeKey: Bool { false }
override var canBecomeMain: Bool { false }
styleMask: [.nonactivatingPanel, ...]
```

編集するにはこれを覆す必要があるが、覆すと**挿入直前の安全確認と衝突する**:

```swift
// InsertionTargetResolver.assertStillCurrent
let app = NSWorkspace.shared.frontmostApplication
```

voinp が最前面になるので「挿入先が変わった」と判定され、**挿入が中止される**。

### 採る案: 編集は別ウィンドウ

| | 方法 | 代償 |
|---|---|---|
| A | HUD を動的に編集可能へ切り替え、挿入前に元アプリをアクティブ化して戻す | フォーカスの往復がタイミング依存。**この種の処理で何度も踏んでいる** |
| **B** | **HUD は表示専用のまま、編集は別ウィンドウで開く** | ウィンドウが 2 つになる |

**B を採る。** HUD の非アクティブ性は苦労して作った性質で、
条件分岐で壊すと戻すのが大変になる。

別ウィンドウでも、挿入前に元アプリへフォーカスを戻す処理は要る。
そこは `awaitingModifierRelease` と同じ「待ってから挿入する」状態として扱う。

## いつ編集するか

**既定は今のまま即挿入。** 猶予を入れると全員が毎回遅くなる。

| 操作 | 動作 |
|---|---|
| いつもどおり離す | **即挿入**（今と同じ速さ。劣化なし） |
| 何かキーを足して離す（例: ⇧ を添える） | 編集ウィンドウを開く |

止める瞬間に決められるので、猶予もモード切替も要らない。
`HotkeyInterpreter` が既に hold / toggle / hybrid を判定しているので、そこに乗る。

## 編集面があると生きるもの

**順番が逆になっている。** 編集面ができて初めて、他の要素が意味を持つ。

| 要素 | 編集面があると |
|---|---|
| **学習ループ** | 成立する。編集前後が自分の面で取れる |
| **候補チップ** | `alternativeTranscriptions` の候補を並べて 1 クリックで差し替え |
| **手動修正率** | 測れる（何文字直したか分かる）。設計書はこれを主指標に据えている |
| LLM 校正 | 再考の材料になる。見て直せるなら自動補正の必然性が下がる |

### macOS のほうが装備が良い箇所

元の設計書が「未解決」としている 2 つに、SDK が答えを持っている。

**候補チップ** — 設計書は「新モデルは N-best を返さない」と自認している。
macOS にはある:

```
DictationTranscriber.ReportingOption:
  volatileResults / alternativeTranscriptions / frequentFinalization
```

**読み → 表記の登録** — `SFCustomLanguageModelData.CustomPronunciation` が
`grapheme` と `phonemes` を持つ。`kintone` → `キントーン` を登録できる。

## 学習信号の選別（設計書から借りる）

確定表示の直後にユーザーがその範囲を編集したら、編集前後を比べる。

| 条件 | 解釈 | 処理 |
|---|---|---|
| かな読みが一致 or 編集距離 1 以内 | **変換誤り**。音は合っていたが表記が違った | 語彙ストアに `読み → 表記` を登録 |
| かな読みが大きく異なる | 音響誤り、または本人の推敲 | 語彙化しない |

音韻一致判定を「補正の制約」ではなく **「学習信号の選別」** に使うのが要点。
ユーザーが文章を推敲しただけの編集を語彙として誤学習しない。

### 未確認: かな読みの取得

漢字交じり文から読みを取る API が macOS にあるかは**確認していない**。
`CFStringTokenizer` に読みを返す機能があった記憶があるが、記憶で断定できない。

**ここが取れないと選別が編集距離だけになり、推敲を誤学習する率が上がる。**
実装前に調べること。

## 進め方

1. **編集ウィンドウを作る**（別ウィンドウ、押し方で開く）
2. **`alternativeTranscriptions` を有効にして候補を並べる**
3. **編集操作を記録する**（まだ学習には使わない。何をどう直しているかのデータを取る）
4. データを見てから**学習ループの選別ルールを決める**

3 を先に入れて実データを見る。元の設計書のフェーズ 0（誤りの実態調査）に相当し、
**想定で作らずに済む。**

## 元の設計書から採らなかったもの

| 要素 | 理由 |
|---|---|
| クラウド STT（二段転写） | [02](02-transcription.md) 参照。実測で速くも正確でもなかった。macOS は 1 エンジンで暫定と確定を両方返すので、二段構成自体が不要 |
| 自動補正を将来やる前提 | 見て直せる面ができるなら、自動補正の必然性は下がる。判断は 3 のデータを見てから |
| グレー → 通常色の置換 | 挿入先を書き換える話。voinp では編集面で完結させる |
