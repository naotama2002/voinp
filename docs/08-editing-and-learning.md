# 08. 編集面と学習ループ

> ステータス: **1（編集ウィンドウ）は実装済み**。2〜4 は未着手。

## これは何か

挿入する前に**確認して直せる面**を voinp に持たせ、その編集操作を
**用語辞書の学習信号として回収する**という設計。

音声入力ウィジェットの設計書（別プロジェクト向け、Web の業務システム）を
読んで、voinp に移せる部分と移せない部分を仕分けた結果として出てきた。

## なぜこれが要るのか

実測で分かっていること（[02](02-transcription.md) のクラウド比較）:

- 誤りの中心は **変換誤り（同音異義）と固有名詞**
- macOS もクラウドも**同じ語で同じように間違える**（`kintone` → 「均等の」）
- つまりエンジンを替えても直らない。**効くのは辞書**

そして辞書を育てるには、**何をどう直したか**が要る。
手で登録させ続けるのは続かない。

## 鍵になった気づき

当初、「voinp はテキストエリアを持っていないので学習ループは成立しない」と
判断していた。挿入は ⌘V かキーストロークで他アプリへ入れて終わりで、
その後ユーザーが何を直したかは観測できないため。

**これは切り分けが雑だった。** 挿入する前に voinp 自身の面で編集させれば、
編集前後が手元で取れる。

重要なのは、**他アプリを覗かないこと**。
[04](04-prompts.md) の「画面の内容を文脈に入れない」という脅威モデルに触れない。
AX で挿入先を監視する案は、この点で筋が悪い。

## ぶつかる場所

HUD は**意図的にキーフォーカスを取らない**作りになっている
（[05](05-ui-input.md) の勘所 6）。

```swift
override var canBecomeKey: Bool { false }
override var canBecomeMain: Bool { false }
styleMask: [.nonactivatingPanel, ...]
```

編集するにはこれを覆す必要があるが、覆すと**挿入直前の安全確認と衝突する**:

```swift
// InsertionTargetResolver.assertStillCurrent
let app = NSWorkspace.shared.frontmostApplication
```

voinp が最前面になるので「挿入先が変わった」と判定され、**挿入が中止される**。

### 採る案: 編集は別ウィンドウ

| | 方法 | 代償 |
|---|---|---|
| A | HUD を動的に編集可能へ切り替え、挿入前に元アプリをアクティブ化して戻す | フォーカスの往復がタイミング依存。**この種の処理で何度も踏んでいる** |
| **B** | **HUD は表示専用のまま、編集は別ウィンドウで開く** | ウィンドウが 2 つになる |

**B を採る。** HUD の非アクティブ性は苦労して作った性質で、
条件分岐で壊すと戻すのが大変になる。

別ウィンドウでも、挿入前に元アプリへフォーカスを戻す処理は要る。
そこは `awaitingModifierRelease` と同じ「待ってから挿入する」状態として扱う。

## いつ編集するか

**既定は今のまま即挿入。** 猶予を入れると全員が毎回遅くなる。

| 操作 | 動作 |
|---|---|
| いつもどおり離す | **即挿入**（今と同じ速さ。劣化なし） |
| 何かキーを足して離す（例: ⇧ を添える） | 編集ウィンドウを開く |

止める瞬間に決められるので、猶予もモード切替も要らない。
`HotkeyInterpreter` が既に hold / toggle / hybrid を判定しているので、そこに乗せた。

### 既知の制限: 修飾キー単独のホットキーでは使えない

`rightCommand` のような修飾キー単独の和音では、**押下中に修飾キーが増えることを
「⌘⇧ のような通常のショートカットだった」と解釈して録音を取り消す**作りになっている
（誤爆防止）。合図と誤爆防止が同じ操作になるため、この経路には乗せていない。
既定の `ctrl+opt+space` はキー付きなので影響しない。

## 編集面があると生きるもの

**順番が逆になっている。** 編集面ができて初めて、他の要素が意味を持つ。

| 要素 | 編集面があると |
|---|---|
| **学習ループ** | 成立する。編集前後が自分の面で取れる |
| **候補チップ** | `alternativeTranscriptions` の候補を並べて 1 クリックで差し替え |
| **手動修正率** | 測れる（何文字直したか分かる）。設計書はこれを主指標に据えている |
| LLM 校正 | 再考の材料になる。見て直せるなら自動補正の必然性が下がる |

### macOS のほうが装備が良い箇所

元の設計書が「未解決」としている 2 つに、SDK が答えを持っている。

**候補チップ** — 設計書は「新モデルは N-best を返さない」と自認している。
macOS にはある:

```
DictationTranscriber.ReportingOption:
  volatileResults / alternativeTranscriptions / frequentFinalization
```

**読み → 表記の登録** — `SFCustomLanguageModelData.CustomPronunciation` が
`grapheme` と `phonemes` を持つ。`kintone` → `キントーン` を登録できる。

固有名詞は読み距離で自動分類できないと分かった（後述）ので、
**反復で拾った語の登録先がここになる。** 優先度が上がった。

## 自動で直せないか（候補の再ランキング）

> 2026-09-20 に `voinp-tools --probe-alternatives` で実測した。**合成音声での測定**。
> 実声での再測が要る。

「認識結果 → ジャッジ → 悪ければ候補を変更」という自動化が可能かを測った。
材料は 2 つあり、**どちらも今のコードでは OFF になっていた**。

| 材料 | 何が取れるか | 今の状態 |
|---|---|---|
| `DictationTranscriber.ReportingOption.alternativeTranscriptions` | N-best 候補 | `reportingOptions: [.volatileResults]` のみ |
| `DictationTranscriber.ResultAttributeOption.transcriptionConfidence` | **区間ごとの信頼度** | `attributeOptions: []` |

### 信頼度は誤りを正しく指す

```
[4] ます。使用が                      ← 実際は「仕様が」
    信頼度: ます。(0.66) 使用(0.30) が(0.29)
[5] 変わったので移動して               ← 実際は「異動して」
    信頼度: 変わった(0.47) ので(0.75) 移動(0.83) して(0.88)
```

正しい区間は 0.7〜0.88、誤った区間は 0.29〜0.47。**閾値が引ける見込みがある。**
LLM を呼ばずに「どこを疑えばよいか」がローカルで分かる。

**ただし取りこぼす。** `移動`（正しくは `異動`）は 0.83 で高い。
信頼度が高いのに間違っている誤りは、この信号では拾えない。

### 候補に正解が入っていないことがある

**ここが決定的だった。** 再ランキング案はすべてこの 1 点に乗っている。

| 語 | 候補 | 再ランキングで救えるか |
|---|---|---|
| `ガルーン` | `[ガルーン, Garoon]` | **救える** |
| `使用が`（正: 仕様が） | `[ます。, ますが、, ます。需要が]` | **救えない**（正解が無い） |
| `銀魂`（正: キントーン） | `[銀魂のレコードを更新します。]` | **救えない**（候補が本命 1 件のみ） |

候補が本命 1 件だけ、という場面が多い。**選び直す余地がそもそも無い。**

### 用語の上限は 64 ではなかった

`docs` に「UI は 100 語、`contextualStrings` は 64 語で、36 語が黙って捨てられる（不具合）」と
書いていたが、**測ったら違った。**

辞書に入れると出力が変わる語（`ガルーン`）を使い、辞書内の位置を動かして効き目を追った。

| `ガルーン` の位置 | 効いたか |
|---|---|
| 1 / 32 / 64 / 65 / 80 / 100 番目 | **効く** |
| 200 / 500 / **1000 番目** | **効く** |
| （対照）辞書に入れない | **効かない** — 出力から消える |

対照で消えることを確かめてあるので、検証自体は機能している。
**64 で頭打ちという事実はなかった。**

ついでに「多すぎるとかえって精度が落ちる」という注記も測った。
この音声に**関係のない語を 1000 件**入れて比べたところ、
辞書なしの出力と**1 文字も変わらなかった**。これも起きていない。

コード側の `prefix(100)` は根拠のない値だったので、
**実測で効くと確かめた 1000** に置き換えた。上限自体は残す
（フレームワークの制限ではなく、設定が壊れていたときの歯止めとして）。

> 留保: 合成音声・日本語のみ・macOS 26.2 での測定。
> 「効く」は「その 1 語が位置 N でも作用した」という意味で、
> 全語が等しく効くことまでは示していない。

### `contextualStrings` が効かない語がある

同じ音声を辞書あり／なしで流して比べた（測定の再現性のため、マイクではなく
音声ファイルを読む道具にしてある）。

- `ガルーン` — 辞書なしでは `ルーン`、辞書ありで本命になった。**効く**
- `キントーン` — `kintone` と `キントーン` の両方を辞書に入れても、
  出力が**1 文字も変わらなかった**。候補にも現れない

辞書に入れれば直るとは限らない。`CustomPronunciation`（読み → 表記）が
要るのはこの型の語だと思われる（未検証）。

### 結論: 選び直すのではなく、疑わしい区間だけ書き換えさせる

| 案 | 判定 |
|---|---|
| 候補から選び直す | **単独では不足。** 正解が候補に無い場面が多い |
| 信頼度で怪しい区間を絞る | **有効。** ローカル・即座・無料 |
| **怪しい区間 + 候補 + 辞書を LLM に渡して直させる** | **射程が一番広い** |

3 番目が今の校正と違うのは、**触ってよい範囲が信頼度で限定される**こと。
いまは文全体を渡して自由に書き換えさせ、[`RefinementGuard`](../Sources/VoinpCore/Refine/RefinementGuard.swift)
で後から縛っている。信頼度で入口を絞れば、**捏造の入り込む余地が構造的に狭まる**。

辞書の射程も伸びる。`contextualStrings` は 64 語で頭打ちだが、
プロンプトには数百語入る。`termHints` が校正プロンプトへ渡っていない
（下記の課題 3）のが、ここで効いてくる。

### 測り方

```sh
# QuickTime Player の「新規オーディオ収録」等で録った音声を渡す
swift run voinp-tools --probe-alternatives ~/Desktop/sample.m4a
swift run voinp-tools --probe-alternatives ~/Desktop/sample.m4a --terms kintone,Garoon
```

マイクではなくファイルを読むのは、**同じ音声で辞書あり／なしを比べる**ため。
喋り直すと条件が変わって比較にならない。
（`AVAudioFile.read` は終端で呼ぶと戻ってこない。`framePosition` で止めること。）

## 判定器を足す（Jev の実測）

> 2026-09-20 に Vercel AI Gateway 経由で実測。**4 例のみ**。合成音声由来のテキスト。

[Jev](https://vercel.com/ai-gateway/models/jev)（TypeSafe AI、2026-09-15 公開）は
**テキストを生成せず、型の決まった判断だけを確率つきで返す**モデル。
`Choice`（最大 255 択）/ `Score` / `Noul`（Yes/No 確率）の 3 つしかない。

生成しないので「怪しい区間を書き換えさせる」用途には使えない。
**候補から選ばせる**用途に限られる ―― そしてそれがこの設計には都合がよい。

### 測った結果

| 入力 | 正解 | Jev の選択 | 確率 |
|---|---|---|---|
| 「使用が変わった」 | 仕様 | **仕様** | 0.61 |
| 「移動してください」（人事） | 異動 | **異動** | 0.82 |
| 「銀魂のレコード」 | kintone | **kintone** | **0.96** |
| 「会議室を移動」（**誤りでない**） | 移動 | **移動** | **1.00** |

4/4 正解。**誤りでない箇所は 1.00 で元のまま**にした（余計な差し替えをしない）。

### 噛み合った 2 つの事実

**1. 信頼度が取りこぼした誤りを Jev が拾った。**
`移動`（正しくは `異動`）は macOS の信頼度が **0.83 と高く**、
信頼度だけでは見つけられなかった。Jev は 0.82 で `異動` を選んだ。
**両者は補完関係にある。** 信頼度だけを入口にすると取りこぼす。

**2. 候補さえ供給すれば選べる。**
`銀魂 → kintone` は N-best に候補が 1 件しか無く、再ランキングでは救えなかった。
**辞書から候補を作って渡したら 0.96 で選んだ。**
エンジンが返さない候補を、辞書側から供給すればよい。

### 漠然と聞いても役に立たない

`Noul` で「この文に変換誤りが含まれるか」と聞いたら **0.56**。
誤りが 2 つある文で、ほぼコイン投げ。

**候補を明示した `Choice` は当たり、漠然とした `Noul` は外れる。**
質問の作り方が精度を決める。

### 3（候補を作る）は実装した

`Sources/VoinpCore/Terms/`。**通信しない。** 外へ出す前に、出す価値のある箇所だけに絞る。

```sh
swift run voinp-tools --match "銀魂のレコードを更新します。" \
  --terms "kintone きんとーん,Garoon がるーん,サイボウズ"
#   「銀魂」 読み=きんたま → kintone(0.40)
```

辞書の 1 行に**読みを添えられる**ようにした（`kintone きんとーん`）。
ASCII の語は自動ではローマ字読みになり（`kintone` → きんとね）、
実際の発音と離れるため。読みを書かない既存の辞書はそのまま動く。

絞り込みは 3 段。実測で誤検出を潰した結果:

| 段 | 効果 |
|---|---|
| 類似度の下限 0.35 | 無関係語（0.25）を落とす |
| **助詞で始まる/終わる塊を捨てる** | 「を更新」が Garoon に 0.40 で当たるのが消える。「銀魂の」も「銀魂」に締まり、差し替えで助詞を巻き込まない |
| **音数の差が 1 以下** | 「移動(いとう)」が「サイボウズ(さいほうす)」に当たるのが消える |

結果（`kintone/Garoon/サイボウズ/グループウェア` の辞書で）:

| 入力 | 出力 |
|---|---|
| 銀魂のレコードを更新します。 | 「銀魂」→ kintone(0.40) |
| 均等のアプリを作ります | 「均等」→ kintone(0.60) |
| ルーンのスケジュールも確認して… | 「ルーン」→ Garoon(0.75) |
| 会議室を移動してください。 | **なし** |
| 今日の天気は晴れです。 | **なし** |
| サイボウズのグループウェアを使います | **なし**（既に正しい） |

**この段は recall 寄りに作ってある。** 拾いすぎた分は後段の判定器が落とす
（実測で、誤りでない箇所は元の表記が 1.00 で選ばれた）。
逆に、ここで落とした候補は後段からは絶対に復活しない。

#### 意図的に壊して分かったこと

長音 `ー` を自前で母音に開くコードを書いていたが、**一度も実行されていなかった**。
`kCFStringTransformHiraganaKatakana` が先に開いてしまうため
（`きんとーん` は変換だけで `きんとおん` になる）。
消してもテストが 1 件も落ちず、そこで気づいた。
いまは変換側の挙動を固定するテストを置き、自前の展開は
**半角/全角ハイフンで読みを書いた場合**にだけ効くものとして残してある。

### 実声で通しで測った（2026-09-20）

それまでの測定はすべて合成音声だったので、24 秒の実録音で確かめ直した。

#### 辞書（`contextualStrings`）は実声では 1 文字も効かなかった

合成音声では `ガルーン` が辞書で本命になったが、**実声では何も変わらなかった**。

```
辞書なし  [4] 金東   [5] やガルーの精神者説明や…
辞書あり  [4] 金東   [5] やガルーの精神者説明や…   ← 同一
```

**辞書の使い道は「認識への事前ヒント」ではなく「事後の候補源」だった。**
合成音声で効いたのは、そちらの方が音が素直だったためと思われる。

#### 信頼度は実声でも誤りを指す。ただし空振りもする

| 箇所 | 信頼度 | 実際 |
|---|---|---|
| 金(0.55) 東(0.47) | **低** | 誤り（正: kintone）✓ |
| ガルー(0.62) | **低** | 誤り（正: Garoon）✓ |
| 採用(0.35) | **最低** | **正しい**（空振り）|
| 精神(0.78) 者(0.81) | 高 | 誤り（正: 製品）**取りこぼし** |

合成音声で見たのと同じ傾向。**信頼度だけを入口にすると、両方向に外す。**

#### 通しの結果: 3 件直り、誤って直した箇所は 0

候補生成（ローカル）が 7 箇所を挙げ、そのうち 3 件が本物、4 件が誤検出。
それを Jev に 1 リクエストで判定させた。

| 箇所 | 候補 | Jev | 判定 |
|---|---|---|---|
| 金東 | kintone | **kintone 0.99** | 直す ✓ |
| ガルー | Garoon | **Garoon 0.97** | 直す ✓ |
| 精神 | 製品 | **製品 0.95** | 直す ✓ |
| 採用 | サイボウズ | **採用 1.00** | 触らない ✓ |
| 検討 | kintone | **検討 1.00** | 触らない ✓ |
| 会社説明 | 製品説明 | **会社説明 0.90** | 触らない ✓ |
| オフィスの説明 | 製品説明 | オフィスの説明 0.55 | 触らない ✓（僅差）|

**7/7。** 閾値 0.8 で差し替えると、3 件直って誤差し替え 0 になる。
7 箇所まとめて 1 リクエスト、1,129 トークン、**$0.000047**。

**候補生成を recall 寄りにした判断は正しかった。** 誤検出 4 件は Jev が全部落とした。

#### 残っている穴

| | |
|---|---|
| **範囲の取り方** | `精神者説明`（正: 製品説明）に対し、短い `精神`→`製品`（0.75）が長い `精神者説明`→`製品説明`（0.70）に勝ってしまう。差し替えると `製品者説明` になり、直り切らない。**類似度が僅差なら長い範囲を優先する**べき |
| 読みの取得 | `金東` の読みが **`きんあすま`** と出た（`東` を人名読みしている）。たまたま当たったが、読みは万全ではない |
| 標本 | **1 本 24 秒、誤り 3 件。** 閾値 0.8 はこの 1 本から置いた暫定値 |

### 成立する流れ

```
1. 認識（信頼度つき）                 ローカル・0 円・0ms
2. 信頼度の低い区間を拾う              ローカル・0ms
3. 読みが近い辞書語を候補として作る     ローカル・0ms
4. Jev に選ばせる                     ~500ms（日本から）・$0.00002/回
5. 確率が閾値を超えたら差し替え
```

2 だけを入口にすると `異動` を取りこぼすので、
**3 で候補が作れた箇所は信頼度によらず 4 へ回す**ほうがよい。
費用は 1 日 100 発話で年 $0.3 程度なので、回数を惜しむ理由がない。

### 留保

| | |
|---|---|
| 標本 | **4 例のみ。** 実声での再測が要る |
| `仕様` の 0.61 | margin が薄い。閾値を 0.8 に置くと差し替えられない |
| 汎用精度 | 公称 67.8%（Opus 5 に 6pt 劣る）。単純な二値での実力は別 |
| **セルフホスト不可** | TypeSafe のマネージド API のみ。**認識テキストが必ず外部へ出る** |
| 運営者 | `operatorKind` は **vendor**（自社運用ではない）。社内承認が別途要る |

## 学習信号の選別

> 2026-09-20 に実測した。**当初の案は誤りだったので差し替えてある。**

### 読みは取れる（確認済み）

```swift
CFStringTokenizerCopyCurrentTokenAttribute(
    tokenizer, kCFStringTokenizerAttributeLatinTranscription)   // 漢字交じり文 -> ローマ字
CFStringTransform(m, nil, kCFStringTransformLatinHiragana, false) // ローマ字 -> ひらがな
```

`kCFStringTokenizerUnitWordBoundary` + `Locale(identifier: "ja")` で作る。
ASCII・絵文字・空白が混ざっても落ちない（属性を持たないトークンは素通しにする）。

### 「編集距離 1 以内」は採ってはいけない

当初 **「読みが一致 or 編集距離 1 以内 → 変換誤り」** と書いていた。**これは誤り。**
19 組で測った、正規化距離（距離 / 長い方の文字数）の並び:

| 正規化距離 | 中身 |
|---|---|
| **0.00** | 8 件すべて変換誤り。推敲は **1 件も混ざらない** |
| 0.25 | `演算 → 円SAN`（辞書◯）と **`やります → やめます`（推敲✗）が同居** |
| 0.29〜0.33 | `非同期処理 → 日時期処理`（◯）と `これを直す → これを消す`（✗） |
| 0.40〜0.57 | `均等の → kintone`（◯）が `デプロイします → リリースします`（✗）と混ざる |

**距離 0 より先は連続的に混ざり、閾値が引けない。**
1 文字でも許すと「やります」→「やめます」を語彙として誤学習する。

### 固有名詞は読み一致では拾えない

**一番直したい語が、この判定では拾えない。**

```
均等の -> kintone     きんとうの / きんとね     0.40
画像   -> ガルーン     がぞう     / がるうん     0.50
```

ASCII がローマ字として読まれる（`kintone` → きんとね）ため、
音が合っていても一致しない。推敲と同じ帯に入る。

### 採る案: 信号を 2 本に分ける

| 経路 | 条件 | 根拠 |
|---|---|---|
| **変換誤り** | 読みが**完全一致**（距離 0） | 実測で偽陽性ゼロ。**1 回で登録してよい** |
| **固有名詞** | 同じ (生, 修正) の組が**繰り返される** | 距離では分離不能。反復のほうが強い信号 |

固有名詞を距離で判別できない以上、「何回直したか」に頼るしかない。
これは進め方 3（記録を先に入れる）を**必須**にする。反復を数えるには記録が要る。

### 実装時の注意（実測で踏んだもの）

| 事象 | 内容 |
|---|---|
| 複数読み | `明日` → **あす**（あした ではない）。読みは 1 つに決め打ちされ、複数読みの語は取りこぼす |
| 数字 | `S3` → **す3**。数字は変換されない |
| 比較範囲 | **差分のあった範囲だけを比べること。** 文全体で比べると長い文ほど距離比が薄まり、推敲が辞書側に紛れ込む |
| 属性なしトークン | ラテン語トークンは transcription 属性を持たない。ここで `nil` を返して全体を諦めると、**ASCII 混在文がまるごと判定不能になる** |

## 実装のメモ（1 を作ったときに分かったこと）

`Sources/VoinpUIKit/Edit/` と、状態機械の `editing` / `restoringFocus`。

| 勘所 | 内容 |
|---|---|
| **確定しても即挿入しない** | 編集すると voinp が最前面になる。そのまま挿入へ進むと `assertStillCurrent` が「挿入先が変わった」と見て中止する。`restoringFocus` を必ず挟み、元アプリが**実際に前面になるまで確認してから**挿入する |
| `activate()` の戻り値を信じない | 「要求を出せた」であって「前面になった」ではない。最前面を実際に確認する |
| 閉じるのが先 | 閉じるのと前面復帰が競ると**自分の編集欄へ貼る**。通知の前に必ず `orderOut` |
| 赤ボタンを拾う | 拾い損ねると `editing` のまま止まり、`acceptsNewSession` が false なので**次の音声入力が一切始まらない** |
| `.regular` へ上げない | 設定ウィンドウと違い、Dock アイコンが一瞬現れて消えるのは目障り。`.accessory` のままでも `NSApp.activate()` でキーウィンドウは持てる |
| ⏎ 単独にしない | `TextEditor` の中では改行になる。確定は ⌘⏎ |
